# v0.2.1-alpha repair plan

- Status: OWNER APPROVED FOR LOCAL IMPLEMENTATION / RELEASE NOT AUTHORIZED
- Supersedes: none
- Baseline: `v0.2.0-alpha` remains frozen
- Trigger: external KG6 black-box audit and local runtime reproduction on 2026-08-28

## Decision boundary

The v0.2.0-alpha package uses the accepted ADR-005 boundary: Windows resolves
SQLite through the operating-system `winsqlite3.dll`. The local reproduction
passed without Python injection, so v0.2.1 should not silently replace that
boundary with a bundled SQLite implementation.

Any move to a private bundled native library would require a separate Owner-
approved ADR covering provenance, licensing, architecture, loading policy,
SBOM, checksum, upgrade, and rollback behavior.

## Proposed work items

### Deferred external evidence: close the second-host runtime gap

1. Run the package on a second independently prepared Windows x64 machine.
2. Keep the environment limited to a compatible .NET 10 runtime and the
   operating-system SQLite component; record installed runtime and OS evidence.
3. Run `version`, `verify-k0-02`, `verify-k0-05`, storage reopen, and the
   package negative cases.
4. Publish the result as `PASS`, `NOT_REPRODUCED`, or `UNKNOWN`; do not convert
   a missing environment into a pass.

### P1: make the prerequisite explicit

1. Change the install and third-party-notice wording from “included by
   published application dependencies” to an explicit Windows prerequisite:
   `winsqlite3.dll` supplied by the operating system.
2. Add a package preflight command that reports the resolved native SQLite
   name and a fail-closed diagnostic when it cannot load.
3. Include the prerequisite and test status in the release manifest without
   pretending that an OS component is part of the ZIP or SBOM.

### P1: repair release identity consistency

1. Make the version used during restore, build, publish, and dependency
   metadata come from one release variable.
2. Ensure `deps.json`, assembly metadata, `PACKAGE_MANIFEST.json`, and
   `RELEASE_MANIFEST.json` all carry the same candidate identity.
3. Add a release gate that fails when a packaged `deps.json` contains the
   previous candidate version.

### P2: strengthen evidence vocabulary

Retain the distinction between package integrity and production readiness:

```text
KG6_RELEASE_PASS = PASS
KG6_PRODUCTION_READY = NO
NATIVE_SQLITE_EXTERNAL_REVERIFY = EXTERNAL / REQUIRED
```

The SQLite question is a runtime evidence item, not permission to bypass the
existing production gate.

This item does not block local candidate construction or subsequent engineering.
Until it is completed, the candidate must retain
`NATIVE_SQLITE_EXTERNAL_REVERIFY=EXTERNAL_REQUIRED` and must not claim broad
Windows-environment coverage.

## Acceptance gates for the local v0.2.1-alpha candidate

- release metadata is internally consistent;
- install instructions state the true OS prerequisite;
- package hashes and SBOM are regenerated and independently checked;
- v0.2.0-alpha compatibility, lifecycle, snapshot, rollback, and removal
  checks still pass;
- `PRODUCTION_READY=NO` remains until external pilot evidence is separately
  satisfied.

The second-host SQLite run remains a publication evidence task. Its absence is
not a source-development failure and is represented explicitly as
`EXTERNAL_REQUIRED` rather than PASS or FAIL.

The Owner authorized local implementation on 2026-08-28. This approval does
not authorize commit publication, push, tag, GitHub/Gitee Release, deployment,
or production use.
